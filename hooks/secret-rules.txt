# SC secret-scanner ruleset.  Format:  <name>@@<regex>   (one rule per line)
# updated: 2026-07-13
# source: gitleaks-style curated (self-identifying provider formats + generic labeled catch-all)
#   - lines starting with '#' and blank lines are ignored
#   - the delimiter is the first '@@'; everything after it is the raw regex (NO PowerShell escaping)
#   - use inline (?i) for case-insensitivity where needed
#   - order matters: first match wins (put specific formats before the generic catch-all)
#
# High-value, SELF-IDENTIFYING provider formats (caught even without a "key =" label) + one broad
# generic labeled catch-all at the end. Seeded from gitleaks-style rules, curated for low false-positive.
# To harden further, sync/extend from the gitleaks default ruleset (see the tracked hardening item).

# --- generic: any secret-LABELED assignment (broadest net; placeholder/env-ref suppressed in code) ---
# PARTIAL hardening 2026-07-13 (guard-audit). KEPT (round-1, tested 20/20, no new false-positives): ["']?
# before the delimiter catches JSON {"api_key":"..."} (the canonical .credentials.json/secrets.json shape,
# which the pre-hardening rule missed); [:=]>? catches the `password => "..."` fat-arrow; value class widened
# to include . ~ = (base64 padding, dotted tokens).
# DELIBERATELY NOT taken further - a 2nd round (compound-label bridging + broadened suppression) was reverted
# because it INTRODUCED regressions (kebab-case config false-positives; a `fixture`/`example` substring in a
# value silently un-blocking a real secret). OPEN DESIGN DECISION: compound/camelCase/all-lowercase labels
# (privateKey, secretKey, secretkey), and a suppression scheme that can't be gamed, likely need an ENTROPY
# heuristic, not more regex.
# Accident-guard, not a DLP.
generic-secret@@(?i)(?:api[_-]?key|secret|token|passwd|password|access[_-]?key|client[_-]?secret|auth[_-]?token|bearer|credential|passphrase|private[_-]?token|pwd)["']?\s*[:=]>?\s*["']?[A-Za-z0-9_\-/+.~=]{16,}
